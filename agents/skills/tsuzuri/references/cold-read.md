# 文脈の無い読み手に通す

このファイルはyomiyasu のあと利用者に渡す前に、文章を文脈の無い読み手に読ませる段階の手順を記述したものです。
書き手は要件定義書・設計書・執筆意図を知っているため、文脈が無いと読むことができない箇所を、自分の文脈で補って読んでしまい認識できません。
その箇所は多くの場合、人のレビューで初めて発見されるため、この段階では文脈を渡さないサブエージェントに先に検出させます。

## 対象にする8つの型

型1〜6は読み手の知識と本文の乖離で、型7は本文の中の主張と例の乖離で生じ、型8だけは不足ではなく、読み手にとって過剰な箇所です。

| 型 | 名前 | 書き手が自分に当てる問い |
|---|---|---|
| 1 | 指すものが決まらない | 主語・目的語・「この」「同じ」「残りの」は、読み手にとって一つに定まりますか。同じ文か同じ段落の直前の文に指す先が1つなら、こそあど言葉で足ります。候補が2つ以上あるときと、段落や見出しをまたぐときだけ名詞を記述します |
| 2 | 呼び名の言い直し・その場の造語 | 抽象的な呼び名を別の抽象的な言い方で言い直していませんか。本文で定義していない言い方をその場で造っていませんか |
| 3 | 借りた言葉を定義せずに使う | 依頼や相手の発言から借りた言葉を使うとき、それが本文で何を指すかを記述しましたか |
| 4 | 誰も言っていないことの否定 | 「Aではなく」の A を、本文か読み手の側で誰が主張したか名指しできますか。できなければ否定を削除します |
| 5 | 前の段落の言い直し | その段落で、前の段落に無かったことを1つ挙げることができますか |
| 6 | 主張の範囲がずれる | その主張は、誰の・どこでの話か記述されていますか。書き手の環境の話が一般論として読まれませんか |
| 7 | 主張と例が合わない | 一般論の文に出てくる人や役割は、そばの例の出来事に実際にいますか。例の中に何人いて何があったかを数え、文の前提と突き合わせましたか |
| 8 | 知らなくても困らない | その文を外したとき、読み手は要件定義書の「6. 読んだあと」のどれができなくなりますか。名指しできなければ `retire` で外します |

型7の役割の語（〜側・担当・チーム）は、読み手が「側＝書いた本人」のように読み替えるため検出できないことがあり、書き手が問いで確認してください。
翻訳調と比喩の動詞は yomiyasu が確認するため、ここでは扱いません。

## 手順

### 1. 自分で当てる

上の8つの問いを自分で当て、検出したものを先に修正してください。
続けて `load` の「前の段落の言い直し」に挙がった段落で、初めて述べていることを1つ挙げ、無ければ段落ごと外し、あればその1点を、理由を述べている段落へ移してください。
この検査は語の重なりしか見ないため、言い換えた要約は拾いません。
同じ用語を節ごとに繰り返し使用する参照用の文書（README など）では誤検知が多いため、挙がった段落を読み、新しい条件・理由・値があれば残してください。

### 2. 読み手に読ませる

`cold` で指示を組み、出てきたものをそのまま、文脈を渡さないサブエージェント1体に渡してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" cold draft.md.tsuzuri
```

指示には要件定義書の「3. 公開する場所と読み手」から組んだ読み手と、各文に ID を付けた本文が入ります。
会話の経緯・元にしたファイル・執筆意図・設計書・前のバージョン・修正箇所は渡さないでください。
どれか1つでも渡すと、読み手は書き手の文脈で補って読み、型1〜3を見落とします。

### 3. 指摘を1件ずつ処理する

読み手が返す「文ID・引用・型・なぜ困るか・直し案」の表を確認し、指摘を1件ずつ、修正するか、修正しない根拠を名指しするかに分類してください（根拠は下の「修正しないときの根拠」）。

### 4. 記録に積む

修正する文は `memo --sid` で新しいバージョンにし、執筆意図が変化しなければ今の執筆意図を、文機能も今と同じものを渡して `write` してください。
抜けが要件定義書や設計書にあれば、SKILL.md の「要件定義書や設計書を改めるとき」の順に戻ってください。
指摘は、修正したかどうかにかかわらず、指摘の付いたバージョンに `review --aspect '推敲：cold-reader'` で記録し、修正しなかったものには理由を記述してください。
この記録はアプリで AI のコメントとしてその文の横に表示されます。

### 5. 必要なら2回目

修正した文が4つ以上か、段落を外した・移したときは、修正したあとでもう一度だけ `cold` から実行してください。
1回目の読み手は再利用せず、新しい読み手を起動します。
2回目の指摘は「3. 指摘を1件ずつ処理する」と「4. 記録に積む」のとおりに処理して終了し、3回目は実施しません。

## 修正しないときの根拠

指摘を修正しないときは、型ごとに次の根拠を名指ししてください。

| 型 | 名指しする根拠 |
|---|---|
| 1・2・3・6 | 読み手がそれを知っている根拠を、要件定義書の「3. 公開する場所と読み手」か本文の前の文から指します |
| 4 | 否定している主張を誰が言ったかを記述します。名指しできなければ否定を削除します |
| 5 | その段落で初めて述べていることを引用します |
| 8 | その文を外すと、読み手が要件定義書の「6. 読んだあと」のどれをできなくなるかを名指しします。名指しできなければ `retire` で外します |

根拠を後から作成して指摘を通さないでください。
「読み手がそう思いそうだから」は理由になりません。
読み手の直し案に本文に無い事実が含まれていたら、材料で確認してから採用し、読み手の推測をそのまま本文にしないでください。
型2・3で、漢語を詰めて造った独自の言い方が拾われたら、事実を1つ追加して終えず、隣の人に口で説明するつもりで、何がどうなるか・なぜか・どんな場合かを改稿してください（考え方は Kazuki Ota「AI の謎な説明文を直すスキル」zenn.dev/microsoft/articles/explain-before-shorten）。
