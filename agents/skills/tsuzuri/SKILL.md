# tsuzuri

このスキルでは、日本語の文章を、要件定義書と設計書を決定してから一文ずつ執筆し、文ごとに執筆前の執筆意図と文機能を記録します。
執筆を終えたら、レビュー・語をそろえる・yomiyasu・文脈の無い読み手を通して利用者に渡し、利用者のコメントを受けたら新しいバージョンで修正します。
人が執筆した文章に文機能を付与してレビューすることもできます。
この SKILL.md は、すべての流れに共通する決まり、記録の保存先、書く・直す・人の文を読むの3つの流れ、文機能の語彙の順に並んでいます。

## 最初に守ること

記録は同梱のスクリプトだけで作成し、ファイル編集ツールなどで記録のファイルを直接書き換えないでください。
執筆意図が文より先にあること、確定したバージョンを書き換えないこと、確定の手順は、スクリプトが守らせているためです。

要件定義書、設計書、一文ずつの本文の順序で執筆してください。
一文ごとには、`memo` で執筆意図を決定し、文を考え、執筆意図・前の文・要件定義書・設計書を読み直して文機能を決定し、`write` で確定する順を守ってください。
文をまとめて作成してから執筆意図を後から付与すると、執筆前の意図をたどることができなくなります。

執筆意図（記録では `memo`）は、この一文で読み手に何をするかという、文を執筆する前に決定する狙いです。
推論の過程や迷った経緯は記述せず、決定した狙いだけを記述してください（記述の仕方は後の「一文ずつ書く」の1にあります）。
執筆した文が執筆意図と異なる方向になったら、執筆意図を修正せず、`write --deviation` にずれと意図の改め方を記述してください。

文機能は一文ごとに付与する5つの判定（接続・重要度・役割・工夫・対応要件）で、正解ではなく、利用者が読んで違和感を覚えたら修正できる目安です。
人どうしでも判定はあまり一致しないため、断定を重ねず、利用者が修正できる形で付与してください。

執筆の途中では語の検査も言い回しの修正もせず、文の働きと執筆意図に集中してください。
語と言い回しは、執筆を終えてから「語をそろえる」と「yomiyasuに通す」で修正します。

一回の依頼で、完成・見直し・検査・受け渡しまで進め、途中で利用者に承認を求めないでください。
ただし利用者が「要件で止めて」「設計で止めて」と依頼したときは、要件定義書か設計書を記録に登録したところで停止し、アプリでコメントを記入してもらってください。

同じ記録への CLI の操作は、一人の書き手を前提にしているため直列に実行してください。
コメントは閲覧アプリ（`app/server.py`）だけが `comments/` に書き込むため、コメントを代筆・編集・削除しないでください。

## 前提と記録の置き場

Claude Code・Codex・Antigravity などのスキル対応 AI コーディングエージェントと Python 3.10 以上を使用し、スクリプトは標準ライブラリだけで動作します。
以下の `<このスキルのフォルダ>` は、読み込んだこの SKILL.md の親フォルダに置き換え、作業フォルダに依存しないよう、常に `python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" ...` の形で呼んでください。

文書 `draft.md` の記録は、隣の `draft.md.tsuzuri/` に置かれます。
`init` だけは文書のパスを、ほかのコマンドは記録フォルダのパスを引数に取ります。

`init` は、git リポジトリのルートの `.gitignore` に `*.tsuzuri/` を追加して記録を既定で git の対象外にし、閲覧アプリのライブラリの文章（`~/.config/tsuzuri/records.json`）に記録フォルダを足します。
記録を git に残したい利用者は、自分で除外の設定を解除して管理します。
利用者には、記録フォルダを git に含めて公開すると執筆意図も公開されることと、git の対象外のまま記録フォルダを削除すると git では復元できないことを伝えてください。

記録フォルダの内容は次のとおりです。

| 中身 | 場所 |
|---|---|
| 要件定義書 | `requirements/rNNN.md` |
| 設計書 | `design/dNNN.md` |
| 執筆意図と文のバージョン | `sentences/sNNNN/` |
| 見出しやコードなどのブロック | `blocks/bNNNN/` |
| タイトルやタグ（frontmatter） | `meta/mNNN.md` |
| 指摘 | `reviews/` |
| コメント | `comments/` |
| 文の並びと、分割・統合の行き先 | `order.json` |

これらは参照してかまいませんが、直接書き換えないでください。

## 1. 書く

### 要件定義書を入れる

要件定義書が無ければ、依頼から次の9つの項目を埋めて、記録フォルダの外の `要件.md` に記述してください。

1. 依頼
2. 書く理由
3. 公開する場所と読み手
4. 範囲と範囲外
5. 制約
6. 読んだあと
7. 書き手の立場
8. 言いたいこと
9. 文章の形

不明な点は仮定と明記して進めて文章の狙いを先に定め、既存の要件定義書や設計書があればそれを使用してください。
執筆を始める前に `examples` で、利用者が以前コメントで修正させた文の前と後を読み、その修正の仕方に合わせて執筆してください。
執筆を始める前に `templates` でテンプレート（本文の見出しの骨組み）を一覧し、依頼でテンプレートの名前を言われたらそのテンプレートを、言われなければ依頼に近いテンプレートを選んでください（近いものが無ければテンプレートを使いません）。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" templates
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" templates README
```

選んだテンプレートは名前を `テンプレート「README」` の形で、テンプレートの「## 文章の形の既定」の節の内容と一緒に要件定義書の「9. 文章の形」に記述し（この形でないと `checklist` がテンプレートの確認項目を加えません）、設計書の段落と見出しのブロックはテンプレートの骨組みに沿って作成してください。
テンプレートは同梱の `references/templates/` と利用者の `~/.config/tsuzuri/templates/` を重ねて読み、同じ名前なら利用者のテンプレートを使用するため、会社や媒体ごとに決まった骨組みは利用者の保存先に追加してください。

利用者が参考の文章を渡してテンプレートの作成を依頼したときは、その文章から用途・文体と分量・見出しの骨組み・繰り返し守られている決まりを読み取ってください。
読み取った内容は、標準のテンプレートと同じ節（冒頭の用途・「## 文章の形の既定」・「## 骨組み」・必要なら「## 確認項目」）で `~/.config/tsuzuri/templates/<名前>.md` に作成し、利用者に見せてください。

各項目に記述すること・記述しないことと、要件定義書と設計書の境目（要件定義書には何を誰のためになぜ執筆するか、設計書にはそれをどう並べるか）は、執筆する前に[要件定義書と設計書に記述すること](references/requirements-and-design.md)で確認してください。
項目ごとに `## <番号>. <項目名>` の見出し（`## 8. 言いたいこと`）を付与してください。
見出しの形が異なると `req` が受け取らず、アプリもこの見出しで項目を切り出すことができません。

書き手の経験は材料に記述されたものだけを使用し、書く作業の事情（文章の中身と関係の無い作業の裏話。使ったツールや、作業環境で確認できなかったことなど）は本文に書かないでください（同じリファレンスの「書き手と、書く作業をする者を分ける」）。
執筆する内容の各項目には「この項目を記述したとき、読み手は何を得るか」と問いかけ、答えられない項目はここで修正してください。
この問いの理由は、[執筆意図の質の確認](references/intent-quality.md)の「要件定義書の段階の問い：誰がたどり着くか」にあります。

新しい記録では、要件定義書の作成、`init`、`req` の順に実行してください。
`req` は初期化された記録を必要とします。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" init draft.md
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" req draft.md.tsuzuri --file 要件.md
```

`req` が返したバージョン（初回は `r001`）を控えてください。

### 設計書を入れる

要件定義書を決定したら、段落ごとの主張と順序を決定して、記録フォルダの外の `設計.md` に記述してください。

- 最初の行に、基づく要件定義書のバージョンを `要件定義書: r001` の形で記述します。
- 段落ごとに `## p<番号> <その段落の主張>` の見出しを付与し、番号は p1 から順に振ります。
- 見出しの下に、前の段落との関係と、その段落が担う要件定義書の項目の番号を記述します。

何を記述し何を記述しないか、執筆の前に何を確認するかは、[要件定義書と設計書に記述すること](references/requirements-and-design.md)の「設計書」と「過不足の確認」にあります。
1段落で終わる文章は設計書を省略できますが、省略するときも執筆を始める前に文の順序を決定してください（同じリファレンスの「設計書を省略してよいとき」）。
設計書は `design` で記録に登録してください。
`design` は、見出しの形が異なる設計書と、頭の行が無いか、頭の行が記録に無い要件定義書のバージョンを指す設計書を受け取りません。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" design draft.md.tsuzuri --file 設計.md
```

`design` が返したバージョン（初回は `d001`）を控えてください。

### 要件定義書や設計書を改めるとき

要件定義書を改めるときは、外の `要件.md` を修正して `req` で新しいバージョンを追加し、続けて設計書の頭の行を新しいバージョンに修正して `design` で追加してください。
古い要件定義書に基づく設計書が最新のまま残ると、`check` が警告します。
設計書の作成の途中で要件定義書を変更したくなったら、設計書の作成を中断して、要件定義書を先に改めてください。
古いバージョンは削除されずに残るため、前の文機能がどのバージョンに照らした判定だったかを後から追跡できます。

### 一文ずつ書く

次の4つの手順（見出しの1〜4）を、最後の文まで繰り返してください。
例の ID とバージョンは説明用のため、実際には `memo` が返した値を使用してください。
また、途中の判断を飛ばしてコマンドをまとめて実行しないでください。

#### 1. 執筆意図を memo で先に確定する

次の一文で読み手に何をするかという狙いを決定し、`memo` で確定してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" memo draft.md.tsuzuri --text '<この一文で読み手に何をするか>'
```

文を考えるのは、執筆意図を決定したあとです。
文機能の判定とレビューは、この執筆意図に照らして行います。
執筆意図は、次の問いで決定してください。

- 前の文までを受けて、この文で何を進めるか
- 読み手にどう受け取ってほしいか、読み手はどう返してきそうか
- この文が無いと何が崩れるか

すべてに答える必要はなく、その文で最も大事な狙いを、決定した結果として短く記述してください。
決定した執筆意図には「この執筆意図を果たしたとき、読み手は何を得るか」と問いかけ、答えられなければ文を考える前に執筆意図を決定し直してください。
理由と、答えられないときのたどり方は[執筆意図の質の確認](references/intent-quality.md)にあります。
推論の過程・迷った経緯・考えの書き出しは記述せず、決定した狙いだけを記述してください。
文の中身の要約（「新しい制度の概要を述べる。」）や手順の名前（「理由を書く。」）だけの執筆意図では、何のためにその文を置くかが残らず、後から執筆意図をたどることができません。

#### 2. 一文を考える

執筆意図に沿って一文だけを考え、次の文はまだ作成しないでください。

#### 3. 文機能を決める

前の文の執筆意図・文機能・段落は `show` で見返し、要件定義書は記録フォルダの `requirements/rNNN.md`、設計書は `design/dNNN.md` を参照してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" show draft.md.tsuzuri
```

`show` は要件定義書と設計書の本文を表示しないため、ファイルを直接参照します。
文機能は、執筆意図に照らして次のように決定してください。

- 役割と接続は、執筆意図（この文で何をするか、前の文を受けて何を進めるか）から決定します。
- 重要度は、「この文が無いと何が崩れるか」から決定します。
- 文の表面の言葉と前後の関係は、執筆意図と食い違っていないかの確認に使用し、文のほうがずれていたら `write --deviation` に記述します。
- 執筆意図が語彙のどの語にも当たらないときは、近い語を無理に選択せず、`review` でそのことを記録します。

#### 4. write で確定する

一文と文機能を `write` で確定してください。
文機能の JSON には `relation`・`importance`・`role`（配列）・`technique`（配列）・`place` を必ず含め、工夫が無ければ `technique` を `[]` にしてください。
説明文の役割の文に小説の工夫を付与するなど、文章の種類と異なる工夫を付与すると `write` が警告します。
`place` には、照らした要件定義書の項目を、見出しと同じ番号と項目名（`8. 言いたいこと`）で記述してください。
設計書のある記録では、文が属する段落の番号を `--para` で指してください（省略すると `write` は受け取りません）。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" write draft.md.tsuzuri --sid s0001 --ver v001 --para p1 --text '<一文>' --tags '{"relation":"段落の始まり","importance":"核","role":["主張"],"technique":[],"place":"8. 言いたいこと"}' --requirements r001 --deviation '<執筆意図からどうずれたか・意図をどう改めたか>'
```

執筆意図からのずれが無ければ、`--deviation` は付与しないでください。
`--requirements` を省くと最新の要件定義書、`--design` を省くと最新の設計書のバージョンに結び付きます。
要件定義書や設計書を改めたら、各文が指す `requirements`・`design` のバージョンと照らし、古いバージョンを指す文機能と段落を見直してください。
文機能だけを修正するときも、`memo` と `write` で新しいバージョンを追加してください。
2文目からも、1〜4を同じ順で繰り返します。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" memo draft.md.tsuzuri --text '<この一文で読み手に何をするか>'
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" show draft.md.tsuzuri
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" write draft.md.tsuzuri --sid s0002 --ver v001 --para p1 --text '<一文>' --tags '{"relation":"補足","importance":"衛星","role":["理由"],"technique":[],"place":"2. 書く理由"}'
```

### 見出し・コード・箱を書く

見出し・コード・画像・表は、文ではなくブロックとして記録してください。
注記の箱・箇条書き・引用・脚注は、中に文を含める入れ物のブロックにします。
見出しやブロックの順序を記録の外で組み立てると、そこに置いた執筆意図をレビューできず、アプリにも表示されません。
ブロックも文と同じく、執筆意図を `memo --block` で先に確定してから、`write --block` で内容を記述してください。
ブロックの執筆意図には、そのブロックを置いたとき読み手が何を得るかを記述し、問いは「一文ずつ書く」の1と同じものを使用します。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" memo draft.md.tsuzuri --block --text '<このブロックで読み手に何をするか>'
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" write draft.md.tsuzuri --sid b0001 --ver v001 --para p2 --block '{"kind":"heading","level":2}' --text '<見出しの文字>' --tags '{"place":"<要件定義書の項目>"}'
```

`--block` の種類は次のとおりです。

| 種類 | `--block` | `--text` |
|---|---|---|
| 見出し | `{"kind":"heading","level":2}`（レベルは1〜4。1は文章のタイトル。Qiita や Zenn のようにタイトルを frontmatter で持つ媒体では1を使わず、`meta` に書く） | 見出しの文字 |
| コード | `{"kind":"code","lang":"css"}`（言語は空でもよい） | コードそのもの |
| 画像・表 | `{"kind":"image"}`・`{"kind":"table"}` | Markdown のまま |
| 注記の箱 | `{"kind":"note","type":"info"}`（info＝情報・warn＝注意・alert＝警告。媒体の書き方は書き出しで変わる） | 空文字列 `''` |
| 箇条書き | `{"kind":"list","ordered":false}` | 空文字列 `''` |
| 引用 | `{"kind":"quote"}` | 空文字列 `''` |
| 脚注 | `{"kind":"footnote","label":"lms"}`（ラベルは英数字・ハイフン・下線） | 空文字列 `''` |

入れ物の中の文は、入れ物を確定したすぐあとに `write --in <入れ物のID>` で一文ずつ記述して並びの上で入れ物の直後に続け、箇条書きは1項目を1文にしてください。
入れ物の中の文が並びの上で入れ物の直後に続いていないと、`check` が誤りにし、`export` は停止します。

脚注は、本文の文に `[^ラベル]` を記述して呼び、その文を確定したあとに脚注のブロックを記述してください。
脚注のブロックと中の文の `--para` は呼ぶ文と同じ段落にし、設計書に脚注だけの段落を作らないでください。
脚注は本文の段落を区切らず、`export` は脚注を本文の末尾に `[^ラベル]: 中身` の形でまとめて出力します。
呼び出しとラベルが1対1で対応しないとき（脚注の無い呼び出し・呼ばれない脚注・同じラベル）と、脚注が呼ぶ文より前にあるときは、`check` が誤りにします。

ブロックの文機能は `place` だけで、役割・接続・重要度・工夫は付与しません。
文機能の語彙は文のために作られていて、ブロックに当てる出典が無いためです。

公開先に向けたタイトルやタグ（frontmatter）は文章の内容ではないため、`meta` で登録し、`---` の行を含めずに内容だけを記述したファイルを渡してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" meta draft.md.tsuzuri --file meta.yaml
```

### 指摘レビューと改善レビュー

執筆を終えたら、指摘レビューと改善レビューを、この順に分けて行ってください。
執筆意図があるため、レビューは「読んでどう感じるか」ではなく「この文は執筆意図を果たしているか」で行うことができます。
指摘しながら修正すると、何がずれていたかが残らず、直しが書き手の好みに流れるため、2つを混ぜないでください。
**指摘レビュー**では、修正せずにずれだけを挙げ、次の観点で確認してください。

- 執筆意図の質：その執筆意図を果たしたとき読み手が何を得るかを問い、答えられない執筆意図は設計書や要件定義書を写していないかまでたどって、元に指摘を付けます（[執筆意図の質の確認](references/intent-quality.md)を読んでから確認します）。
- 執筆意図と文：その文が執筆意図を果たしているか、その執筆意図を果たしているのが別の文になっていないかを確認します。
- 文機能と執筆意図：文機能が執筆意図から定まる語になっているか（文機能の真偽）と、先頭の役割がその文の最も強い働きになっているかを確認します。
- 一文の働きの数：説明文の役割が3つ以上付いた文は、分割できないかを確認します（`write` も警告を出します）。
- 要件の網羅：担当の文が無い要件や、どの要件にも当たらない文が無いかを確認します。
- 設計書との照合：`show` の `para` で段落ごとに文をまとめ、段落が実際に言っていることを一文で抜き出して設計書の主張と比較し（リバースアウトライン）、違えば文がずれたのか設計書を改めるべきだったのかを指摘に書きます。
- 重要度と分量：核が埋もれて衛星の説明ばかり長くなっていないかを確認し、`load` の「衛星の要否」に並ぶ衛星の文ごとに「外すと、読み手は要件定義書の「6. 読んだあと」の何ができなくなるか」と問い、名指しできない衛星には外す指摘を出します。
- 読み手の負担：`load` で衛星の多い段落・長い文・読点の多い文・前の段落の言い直しの候補を提示し、同じことを二度言っている文が無いかを通して読みます（[読み手の負担の確認](references/review-load.md)を読んでから確認します。候補は見直す順番で、削れという判定ではありません）。
- 接続：前の文と文機能の接続のとおりにつながるかを確認し、`load` の「接続の確認」に並ぶ接続語と接続助詞（〜ても・〜が・〜ので・そのため・一方で）ごとに「何に反して〜なのか」「何が理由で〜なのか」を言葉で説明できるかを問い、説明できなければ指摘を出します。
- 主語：主語を省いた文は、上から読んできた読み手が動作主を1つに特定できるかを確認し、段落の頭・見出しの直後・直前と動作主が変わる文でだけ主語を記述します（`load` の「途中で変わる動作主」に並ぶ、動作主を省いた前半と主語の違う後半をつないだ文も見ます。直前の文と同じ主語は書かず、並べた語を受け直すときは「それ」で足ります。`load` の「くり返す名詞」が候補を出します）。
- 初めて出る語：`load` の「初めて出る語の主題」に並ぶ文で、読み手の知らない語を導入せずに「は」の主題にしていないかを確認し、していれば「〜がある」の形で導入してから主題にする案を出します。
- 文体と言い回し：すべての文が要件定義書の「9. 文章の形」で決定した文体（口語か文語か）にそろっているか、文語の文書で日常的な和語（書く・分かる・頼む）より定着した漢語（執筆する・理解する・依頼する）を使っているか、`load` の「可能動詞の短い形」に並ぶ文（読める・開けます）を「〜することができる」か漢語にしているか、`load` の「主題と述語の同じ語」に並ぶ「〇〇の××は、△△の××です」の形の文が無いか、長い一続きの対象を「」でくくれば読みやすくならないかを見ます。
- 見出しとタイトル：`load` の「見出しと、その下の主張と核」を参照し、見出しごとに、その節で言いたいことを字数を気にせず一文で記述し、主張と核の文の情報に読み手にとっての優先順位を付けて、見出しが最上位の情報から始まっているか、曖昧な一語（差・違い・変化など）に複数の情報を詰め込んでいないかを見ます（タイトルは要件定義書の「8. 言いたいこと」と照らします）。
- 執筆意図どおりに執筆できたか：ずれがあれば、そのずれの記録と意図の改めがあるかを確認します。

指摘は `review` で対象の文・バージョンと観点を記録し、観点の頭に「指摘：」を付与してください。
指摘を修正しないと決定したときや別の文で修正したときは、指摘の付いたバージョンに `review --aspect '対応：<何をしたか>'` を記録してください（アプリの「未解決」は、対応の記録が無い今のバージョンへの指摘だけを数えます）。
要件の抜けは、その内容を担うべき文に結び付けてください。
指摘が無ければ、無理に作らないでください。
**改善レビュー**では、指摘ごとに、執筆意図を満たす修正案を提示してください。

- 案は、その文の執筆意図を最もよく果たす形にし、書き手の好みの言い回しへ寄せません。
- 執筆意図そのものが弱いとき（執筆意図が文章全体の要件につながっていない、前後の文と執筆意図が重なる）は、執筆意図の修正案も提示します。
- 文機能が語彙の語に当たらなかった文には、語彙を追加する案か、文を分割・統合する案を提示します。
- 見出しとタイトルの指摘には、最上位の情報を前に出す案を中心に、狙いの違う案（主張を最も明確にする・元の対比を残す・問いにする）を2〜3提示し、どれを勧めるかと理由を添えます。

改善の案は `review` で記録し、観点の頭に「改善：」を付与してください。
執筆の依頼の中では、改善の案を自分で反映し、指摘の付いた文を「2. 直す」と同じ手順で新しいバージョンにしてください。
ただし、材料に無い事実が必要な案と、意味・数値・確かさ・強さが変わる案は反映せず、指摘の付いたバージョンに `review --aspect '対応：<反映しない理由>'` を記録して、利用者に伝えてください。
反映した文はもう一度指摘レビューで確認し、そこで出た指摘の反映は1回までにして、それでも残る指摘は利用者に伝えてください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" review draft.md.tsuzuri --sid s0002 --ver v001 --aspect '指摘：文機能の真偽（role）' --text '<直さずに挙げるずれ>'
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" review draft.md.tsuzuri --sid s0002 --ver v001 --aspect '改善：執筆意図と文' --text '<執筆意図を満たす直し方と、修正の案>'
```

`check` で記録の整合を確認し、`export` で本文を再生成してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" check draft.md.tsuzuri
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" export draft.md.tsuzuri
```

`check` の終了コードは、0 が整合、1 が不整合、2 が実行時の誤りで、表示と終了コードの両方を確認してください。
時計のずれの警告は、PC の時計が戻って執筆意図の時刻が文の時刻より後になったときに表示されますが、通知するだけであるため終了コードが 0 のこともあります。
不整合や実行時の誤りを残したまま成功と伝えず、自分の記録の誤りは新しいバージョンで修正し、修正できないものは利用者に伝えてください。
`check` は意味や文機能の妥当性までは判定しないため、文機能のレビューを省かないでください。

`export` は、最新の文とブロックから記録の中の `text.md` を記事の Markdown として再生成し、`meta` があれば頭に frontmatter を付与します。
元の `draft.md` は上書きしません。
公開する媒体の方言は `--flavor`（`gfm`・`qiita`・`zenn`。既定は GitHub の Markdown の `gfm`）で、要件定義書の「9. 文章の形」に記述した媒体に合わせて選択してください。
方言で変わるのは注記の箱の記法だけで、記録は媒体によらず同じ形です。
段落は、設計書があれば文の `para` が変わる箇所で、設計書が無ければ `relation: "段落の始まり"` の箇所で区切り、ブロックの前後でも区切ります。

### 語をそろえる

レビューのあと、yomiyasu に通す前に、校正辞書に当たる語を統一してください。
yomiyasu は原文の語の選び方を変えないため、和訳しすぎた外来語や、利用者が決定した呼び名と異なる語は、ここで修正しないと残ります。

1. `words` で、最新のバージョンの文・執筆意図・見出しや箱の字に校正辞書を当て、当たった箇所の一覧を出力します（辞書は、このスキルの `references/words.tsv` と、利用者の `~/.config/tsuzuri/words.tsv` があればそれを重ねて読みます）。
2. 当たった箇所は1か所ずつ前後を読み、辞書の補足に合う意味で使用しているときだけ、文として自然になるように修正します（同じ字で別の意味の語があるため、一覧のまま置き換えません）。
3. 修正した文ごとに `memo --sid` で新しいバージョンを作成し、執筆意図にも当たったら修正した執筆意図を、当たらなければ今の執筆意図をそのまま渡し、文機能は今のバージョンと同じにして `write` します。
4. 修正前のバージョンに `review --aspect '推敲：語'` で、どの語をどう修正したかを記録します（観点の頭の「推敲：」は、指摘ではなく語や言い回しを修正した記録だという印です）。
5. 辞書の補足に「要相談」とある語は修正せず、`review` の「指摘：」として記録して利用者に伝えます。
6. 修正を終えたら `drift` で、修正前のバージョンと比較して否定・数値・確かさ・強さの語が変わった文を出力し、変わった文は語の直しではないため、直す前の文をそのまま新しいバージョンとして `write` して元に戻します。
7. 戻した文は次の `drift` でも直前のバージョンとの差として出力されるため、`drift --since <直す前のバージョン>` で修正前と現在を比較し、差が出なければ復元できています。

### yomiyasuに通す

語をそろえたあと、利用者に渡す前に、本文を yomiyasu で推敲してください。
言い回しの引っかかりを先に解消しておくと、利用者は要件・設計・執筆意図のずれのような、人にしか判断できないことに集中して読むことができます。

1. `export` で `text.md` を生成し、記録フォルダを作業フォルダにして yomiyasu をかけます（yomiyasu は作業フォルダの外のファイルを参照しません）。
2. yomiyasu には、要件定義書と設計書の最新（記録フォルダの `requirements/rNNN.md` と `design/dNNN.md`）を `--material` で資料として渡します。
3. 要件定義書の「3. 公開する場所と読み手」から読み手（`--reader` の expert・informed・general）を、「9. 文章の形」から文書の種類（`--doc-type`）を決定して渡し、「7. 書き手の立場」の書き手と読み手の関係を依頼に書きます。
4. yomiyasu が修正した文ごとに `memo --sid` で新しいバージョンを作成し、執筆意図は今のバージョンのまま、文機能も今のバージョンと同じにして `write` します。
5. 修正前のバージョンに `review --aspect '推敲：yomiyasu'` で、何をどう修正したかを記録します。
6. 意味・強さ・事実が変わる修正と、材料に無い事実を削除するか追加する修正は記録に含めず、`review` の「指摘：」として記録して利用者に伝えます。
7. 修正を終えたら `drift` で、修正前のバージョンと比較して否定・数値・確かさ・強さの語が変わった文を出し、変わった文は前の手順と同じく直す前の文を新しいバージョンとして書いて戻し、`review` の「指摘：」に回します。
8. もう一度 `export` し、`check` を通します。

資料が無いと、yomiyasu は本文の事実や主張が要件どおりかを照合できず、言い回しだけを確認します。
yomiyasu は、言われなかった読み手と立場を推定しません。
意味の変わる修正を記録に含めないのは、言い回しの修正に見えても、要件定義書や設計書の誤りから来ていることがあるためです。
「2. 直す」で修正した文も、渡す前に「語をそろえる」・この手順・「文脈の無い読み手に通す」を通してください。
記録の外（媒体のドラフトなど）で直接修正すると記録と公開する本文がずれるため、修正は必ず記録の新しいバージョンで行ってください。

### 文脈の無い読み手に通す

yomiyasu のあと、利用者に渡す前に、本文を文脈の無い読み手に読ませてください。
書き手は要件定義書・設計書・執筆意図を知っているため、指すものが定まらない語や、前に説明していない呼び名、読み手には不要な文に自分では気づくことができません。
小説・物語の本文には使用しません。

手順・8つの型・指摘の処理の仕方は、執筆の前に[文脈の無い読み手に通す](references/cold-read.md)で参照してください。
`cold` は、要件定義書の「3. 公開する場所と読み手」と、文の ID を付与した本文だけで読み手への指示を組み立てます。
その指示を、文脈を渡さないサブエージェント1体に渡し、返ってきた指摘を文ごとに処理して、`review --aspect '推敲：cold-reader'` で記録してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" cold draft.md.tsuzuri
```

修正したら、もう一度 `export` し、`check` を通します。
文脈の無い読み手の指摘で修正した文も、`drift` で、否定・数値・確かさ・強さの語が意図せず変わっていないかを確認してください。

### 渡す

渡す前に、`checklist` で確認項目を一覧し、残っている項目を1つずつ本文で確認してください。
確認項目は、どの文章にも当てる標準の項目（[確認項目](references/checklist.md)）と、使用したテンプレートの「## 確認項目」の節の項目です。
確認した項目は、確認した文の ID と確認した内容を `confirm` で記録し、機械で判定する項目は、判定を通過するまで文を修正してください。
確認のあとで本文を修正すると、その項目は「確認後に変更」に戻るため、もう一度確認してください。

渡すときは、各文の執筆意図と文を、要約や抜き出しをせずに記録から出力したまま並べて提示してください。
あわせて、`draft.md.tsuzuri/text.md` と記録フォルダの場所、反映した改善と反映しなかった指摘（無ければその旨）、`check` の結果と警告を伝えてください。

## 2. 直す

まず `comments` で利用者のコメントを確認してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" comments draft.md.tsuzuri
```

コメントが付いた文の `sid`・`ver` と今の本文を照らし、古いバージョンへの指示を今の文への指示と取り違えないでください。
修正するのは `status` が `open` のコメントです。
コメントの付いたバージョンより新しいバージョンを記録すると、そのコメントは対応したバージョン（`addressed_by`）が付いて `resolved` として読まれ、直っていなければ利用者がアプリで開き直します。
コメントのファイルは変更しないでください。

「行き先の無いコメント」は、指す文の ID が記録の今の並びにも分割・統合前の文の記録にも無いか、指すバージョンが無いコメントです。
行き先の無いコメントや使用できなくなったコメントは、削除したり別の文への指示だと決めつけたりせず、利用者に伝えてください。
分割・統合で置き換えられた元の文へのコメントは、`order.json` の `retired` にある移行先をたどって確認してください。

`doc` を持つコメントは、文ではなく要件定義書（`requirements`）の項目か設計書（`design`）の段落へのコメントで、`item` は要件定義書なら項目の番号（`8`）、設計書なら段落の番号（`p2`）、`current_text` はその項目の最新の見出しと本文です。
要件定義書へのコメントがあれば、文より先に要件定義書を修正して `req` で追加し、設計書の頭の行を修正して `design` で追加してから、影響する文を修正してください（「要件定義書や設計書を改めるとき」と同じ順です）。
要件定義書と設計書へのコメントは、その項目の見出しか本文が新しいバージョンで変わったときに対応済みとして読まれ、別の項目だけを修正したバージョンでは開いたままです。

対象の文ごとに `memo --sid` で修正の新しいバージョンを作成し、前のバージョンを残して、コメントから変更を追跡できるようにしてください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" memo draft.md.tsuzuri --sid s0001 --text '<直したあとの、この一文で読み手に何をするか>'
```

一文を考え、執筆意図・要件定義書・設計書・`show` で見返した前の文と照らして文機能を決定し、返されたバージョンで `write` してください。
先頭の文には、前の文が無いものとして文機能を決定します。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" write draft.md.tsuzuri --sid s0001 --ver v002 --para p1 --title '<何を直したか>' --text '<直した一文>' --tags '{"relation":"段落の始まり","importance":"核","role":["主張"],"technique":[],"place":"8. 言いたいこと"}'
```

v002 以降のバージョンには、何を直したかを、コミットの件名のように1行（40字以内）で `--title` に記述してください。
タイトルはアプリのバージョン履歴に表示され、省くと `write` が警告します。
コメントが語や言い回しの言い換え（「版」を「バージョン」に、「頼む」を「依頼する」に）で、ほかの文章にも同じ直しが要りそうなときは、利用者の校正辞書（`~/.config/tsuzuri/words.tsv`）に「探す形・直す先・補足」をタブ区切りで1行追加してください。
追加する前に今の記録へ `words` を当て、直さない語（「英語版」の「版」など）に当たらない探す形に絞り、補足には直す意味の範囲とコメントの ID を記述してください。
その文章だけの事情による直しは追加せず、追加した行は利用者に伝えてください。

### 文を分ける・まとめる

文を分割・統合するときは、元の ID を `memo --from` にカンマ区切りで渡して、新しい ID の文を作成してください。
分割するときは分割した各文に同じ元の ID を渡し、統合するときは元の ID を複数渡します。
分割・統合は、`--sid` での修正と混ぜないでください。
コメントを元のバージョンに残したまま、行き先を記録するためです。
例として2文目を分割するときは、前半と後半のそれぞれについて、同じ元の ID から執筆意図を作成し、一文を考え、文機能を決定して確定します。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" memo draft.md.tsuzuri --from s0002 --text '<前半の一文で読み手に何をするか>'
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" write draft.md.tsuzuri --sid s0003 --ver v001 --para p1 --text '<前半の一文>' --tags '{"relation":"補足","importance":"衛星","role":["解説"],"technique":[],"place":"9. 文章の形"}'
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" memo draft.md.tsuzuri --from s0002 --text '<後半の一文で読み手に何をするか>'
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" write draft.md.tsuzuri --sid s0004 --ver v001 --para p1 --text '<後半の一文>' --tags '{"relation":"順接","importance":"衛星","role":["解説"],"technique":[],"place":"9. 文章の形"}'
```

分割した2文を統合するなら、両方の ID から執筆意図を作成してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" memo draft.md.tsuzuri --from s0003,s0004 --text '<まとめた一文で読み手に何をするか>'
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" write draft.md.tsuzuri --sid s0005 --ver v001 --para p1 --text '<まとめた一文>' --tags '{"relation":"補足","importance":"衛星","role":["解説"],"technique":[],"place":"9. 文章の形"}'
```

### 文を外す・動かす

文を本文から外すときは、`retire --sid <文のID> --text <外す理由>` を使ってください。
文の内容は記録に残り、理由は `review` の「削除」として残ります。
外したい文を隣の文と `memo --from` で統合する形で外すと、統合した先の執筆意図に削除の理由が入るため、その形で外さないでください。
執筆意図には、その文で読み手に何をするかだけを記述し、削った・短くした・重ならないようにした、のような修正の理由は `review` に記録してください。

文の内容を変えずに順序だけを変更するときは `move` で移動し、文のバージョンは増やしません。
並べ替えは段落の組み立ての変更であるため、先に設計書を新しいバージョンにして、段落の主張と順序を合わせてください。
入れ物のブロック（注記の箱・箇条書き・引用・脚注）は中の文と離れるため、`move` では移動できません。
新しい文とブロックは並びの末尾に追加されるため、文章のタイトル（見出しのレベル1）を後から頭に置くときは `--after start` で先頭へ移動してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" move draft.md.tsuzuri --sid s0004 --after s0001
```

修正した文と移動した文の後ろの文も、接続の文機能が合うかを見直し、移動して段落の先頭になった文は、接続を「段落の始まり」にした新しいバージョンにしてください。
修正を終えたら「書く」と同じ観点でレビューし、指摘を `review` に記録し、`check` と `export` を実行して、本文・記録・指摘・検査の結果を渡してください。

## 3. 人の文を読む

人の文を読むときは、まず元の文章を一文ずつに区切ってください。
句点・？・！のあとで切りますが、かぎ括弧の中の句点では切らず、閉じかぎ括弧を取り残さないようにしてください。
あわせて、段落の切れ目も控えておいてください。
原文の語を修正せずに、文ごとの働きを読むためです。

要件定義書が無ければ、9つの項目を推定して `## <番号>. <項目名>` の見出しで外のファイル `推定要件.md` に記述し、最初の行に「**推定した要件**」と記述して、利用者の明示した要件と混ぜないでください。
設計書は推定しません。
段落が2つ以上ある文章では `check` が設計書の無いことを警告しますが、人の文では問題として扱わないでください。
記録を作成し、`req` で推定した要件定義書を登録してください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" init human.md
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" req human.md.tsuzuri --file 推定要件.md
```

一文ずつ、前の文と要件定義書に照らして、まず `memo --inferred` で推測した執筆意図を記録し、続けて `write --human` で文機能を付与してください。
人の文には書き手の執筆意図が無いため、その文が何をしているかを文と前後から推測し、読み取ることができない点は「不明」と記述して、意図を作り込まないでください。
推測した執筆意図には `by: inferred` の印が付いて書き手の意図と分けて記録され、アプリでは「tsuzuri で執筆した文ではないため推測」と添えて表示されます。
ID とバージョンは、省くと自動で付きます。
人の文の箇条書きで1項目に2文以上あるときは、2文目から `--cont` を付けて、前の文と同じ項目に続けてください。

チャット AI が書いた文章を読むときは、[書いた経緯の書き出し](references/session-log-prompt.md)のプロンプトを、利用者にその会話へ貼ってもらってください。
返ってきた答えの確かさが「会話にある」の文は `memo --reported` で、「推定」の文は `memo --inferred` で執筆意図を残します。

記録を人と共有するときは、`pack` で記録と文書を1つの `.tsz` にまとめ、受け取った人は `unpack` で展開します。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" memo human.md.tsuzuri --inferred --text '<文と前後から推測した執筆意図>'
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" write human.md.tsuzuri --human --text '<人が書いた一文をそのまま>' --tags '{"relation":"段落の始まり","importance":"核","role":["主張"],"technique":[],"place":"8. 言いたいこと"}'
```

レビューは「書く」と同じく指摘レビューと改善レビューを分けて行いますが、「執筆意図どおりに執筆できたか」は対象外です。
また、推定した要件定義書と異なるだけで誤りだと断定しないでください。

```bash
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" review human.md.tsuzuri --sid s0001 --ver v001 --aspect '指摘：要件の網羅（place）' --text '<指摘>'
python3 "<このスキルのフォルダ>/scripts/tsuzuri.py" check human.md.tsuzuri
```

人の文では改善の案を自分で反映せず、記録の場所、推定した要件定義書、指摘と改善の案、検査の結果を渡してください。
ただし、利用者自身のドラフトや「評価して直して」と依頼された文章のように、利用者が直す立場にある文章では、反映してよいかを、反映する案の範囲を選択肢にして利用者に確認してください。
他人の記事や公開済みの文章を読むだけの依頼では確認せず、反映を求められたときに「2. 直す」で行ってください。

## 文機能の語彙

文機能の判定に迷ったときは、[文機能の語彙](references/tag-vocabulary.md)の「確かめ方／外すとき」の欄を参照してください。

- 接続 `relation`：市川孝の文の連接8類型（順接・逆接・添加・対比・転換・同列・補足・連鎖）を使用し、最初の文や段落をまたぐ遠い関係は `段落の始まり` とし、文内の節の関係は付けません。
- 重要度 `importance`：核・衛星の2値で、その文を削除しても要件定義書の「言いたいこと」が残るなら衛星、欠かせないなら核とします。
- 役割 `role`：説明文は木戸の6つ（主張・評価・理由・根拠・解説・報告）から選択し、一文が複数の働きを持つときはすべて含めて最も強い働きを先頭に配置します（先頭が主の役割として色とアイコンになり、2つ目以降は副の役割として添えられます）。
- 小説の役割は、深度（外面・感覚・内面・生の声）と話法（語り・直接話法・間接話法・自由間接話法・直接思考・自由間接思考）を配列に含めます。
- 工夫 `technique`：小説ではシャレード・描写・記号での回収・フォーカスの予告・五感・「欠落を書く」・「文長を揺らす」、説明文では関係の明示・否定の根拠・対比定義・譲歩・命題の書き出し・誤解の先回りから、実際に使ったものだけを入れます（出典の箇条はリファレンスでたどります）。
- 対応要件 `place`：要件定義書の項目を見出しと同じ番号と項目名で指し、照らしたバージョンは `write --requirements` で結び付けます（設計書の段落は文機能に含めず、`write --para` で記録します）。

語彙を追加したいときは、利用者が記録フォルダの `vocab.json` に追加します。
これは利用者のための設定で、確定した記録を直接書き換えてよいという許可ではありません。
現在の CLI が拡張を読み込む欄は `relation` と `role` だけで、値は語の配列です。

```json
{"relation":["応答"],"role":["案内"]}
```

工夫 `technique` に未知の語を含めると保存はできますが警告が表示され、`vocab.json` に追加してもその警告は消えません。
重要度 `importance` の語は、核・衛星の2つから増やすことができません。
語を追加するときは、意味・出典・確認の仕方を利用者と共有し、既定の語彙で足りるなら増やさないでください。
